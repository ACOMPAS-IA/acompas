## 0. Puntos confirmados por Luis del Olmo en la revisión de la PR #68

| Nº | Punto | Decisión | Motivo |
| --- | --- | --- | --- |
| P1 | Herramienta de arranque y lenguaje | Vite con la plantilla de React en TypeScript, con `strict: true` en `tsconfig`. | Ninguna fuente fijaba la herramienta ni el lenguaje del frontend. Vite es el arranque estándar de React y TypeScript detecta errores de contrato antes de ejecutar. |
| P2 | Versión de Node y cómo se fija | Node 24 (LTS). Se fija en tres sitios coherentes: la imagen base del Dockerfile (`node:24-<variante>` con versión menor y parche explícitos), `engines.node` de `package.json` y un `frontend/.nvmrc` que usa la CI. | Una sola versión en local, contenedor y CI evita diferencias entre entornos. |
| P3 | Gestor de paquetes y versiones de dependencias | npm (incluido en la imagen de Node), con `package-lock.json` en el repositorio e instalación con `npm ci`. | Evita añadir otro gestor (pnpm, yarn) y hace la instalación reproducible. |
| P4 | Ejecución del frontend | Servicio `frontend` de Docker Compose que ejecuta el servidor de desarrollo de Vite, con el código de `frontend/` montado para recarga en caliente y `node_modules` en un volumen del contenedor. No hace falta instalar Node en el equipo anfitrión. | Coherente con el entorno de referencia en Docker y con el README, que indica que no hace falta instalar Node.js en el anfitrión (`README.md`, `README.es.md`). |
| P5 | Puerto | Puerto configurable con `FRONTEND_PORT` (por defecto 5173, el de Vite), publicado solo en el anfitrión local como `127.0.0.1:${FRONTEND_PORT:-5173}:5173`. Dentro del contenedor, Vite escucha en `0.0.0.0`. La variable `FRONTEND_PORT` se añade a `.env.example`, como `POSTGRES_PORT` y `KEYCLOAK_PORT`. | Mismo criterio que Keycloak en ACO-011: el servicio de desarrollo no queda expuesto a la red. |
| P6 | Usuario del contenedor | El servicio se ejecuta con el usuario sin privilegios `node` de la imagen. | Los ficheros que el contenedor crea en un directorio montado quedarían, si no, con propietario `root` en el anfitrión (ya ocurre con `infra/keycloak/import`). |
| P7 | Tests de este ACO | Una prueba mínima con Vitest, `jsdom` y Testing Library que monta la aplicación y comprueba que pinta su contenido inicial. Las pruebas con navegador quedan fuera de este ACO. | Vitest comparte configuración con Vite. |
| P8 | Comprobaciones de la CI | Un job `frontend` en `.github/workflows/ci.yml`, independiente del de backend, que instala con `npm ci` y ejecuta estilo (`npm run lint`), tipos (`npm run typecheck`) y tests (`npm test`). Node se instala en el runner con `actions/setup-node` leyendo `frontend/.nvmrc`. | Ninguna fuente fijaba cómo se comprueba el frontend en la CI. |
| P9 | Herramienta de estilo | ESLint con TypeScript y las reglas de hooks de React y de refresco. Sin Prettier. | Herramienta de estilo más extendida en React; es la configuración que traía la plantilla de Vite hasta su versión actual. |
| P10 | Preparación para móvil | `index.html` incluye `<meta name="viewport" content="width=device-width, initial-scale=1">` y `<html lang="es">`. El diseño adaptable no se hace aquí. | La aplicación debe usarse en móvil; el diseño adaptable corresponde a ACO-017. |
| P11 | Estructura inicial preparada para las pantallas del Sprint 1 | `src/main.tsx` (punto de entrada), `src/App.tsx` (componente raíz, que pinta el nombre ACOMPAS) y los directorios vacíos `src/pages/` y `src/components/` (con `.gitkeep`), donde ACO-017 y ACO-018 añadirán sus pantallas y componentes. Sin enrutador ni biblioteca de componentes. | Concreta «estructura inicial preparada para las pantallas del Sprint 1» sin adelantar decisiones de layout o navegación, que son de ACO-017. |
| P12 | Versión de React | React 19 (y `react-dom` 19), con la versión exacta fijada en `package-lock.json`. | Es la versión mayor estable actual, la que instala la plantilla de Vite. |

## 1. Identificación

- **ID:** ACO-016
- **Nombre:** React bootstrap

El responsable, el soporte y la revisión, la estimación y las dependencias de este ACO son los de la matriz operativa del Documento Operativo del sprint en curso, que es su fuente única. Esta ficha no los repite.

## 2. Objetivo

Crear la base mínima del frontend React para ACOMPAS.

## 3. Incluye

1. Aplicación React ejecutable localmente: proyecto en `frontend/` creado según P1, con Node según P2 y dependencias según P3 y P12.
2. Estructura inicial preparada para las pantallas del Sprint 1, según P11, y preparada para pantallas estrechas según P10.
3. Integración compatible con el entorno de desarrollo existente: servicio `frontend` en `docker-compose.yml` según P4, P5 y P6; job de CI según P8; instrucciones de arranque en el README.

## 4. Resultado esperado

- `docker compose up -d --build` levanta también el servicio `frontend`, sin Node instalado en el anfitrión.
- `http://localhost:5173` (o el puerto de `FRONTEND_PORT`) sirve la aplicación, que pinta el nombre ACOMPAS.
- Dentro del contenedor, `npm run lint`, `npm run typecheck` y `npm test` terminan sin errores.
- La CI ejecuta esas tres comprobaciones en cada PR a `main` y queda en verde.

## 5. Fuera de alcance

No forman parte de ACO-016:

- Layout de la aplicación y diseño adaptable a móvil (ACO-017).
- Login y cualquier integración con Keycloak (ACO-018).
- Cliente del API backend, proxy hacia el backend y CORS (ACO-019).
- Pruebas con navegador y tests E2E (ACO-033; ver P7).
- Enrutado, gestión de estado y bibliotecas de componentes o estilos.
- Build y servicio del frontend para producción.

## 6. Relación con otros ACO

Las dependencias de este ACO se consultan en la matriz operativa del Documento Operativo del sprint en curso.

- **ACO-017 (Layout)**, **ACO-018 (Login)** y **ACO-019 (API client)** construyen sobre este proyecto: reciben `frontend/` con `src/App.tsx` como componente raíz, los directorios `src/pages/` y `src/components/` (P11), los scripts `lint`, `typecheck` y `test`, y el servicio `frontend` de Docker Compose.
- **ACO-032 (Flujo E2E)** integra el frontend en el flujo extremo a extremo.

## 7. Restricciones técnicas

- No se introduce en el frontend ningún secreto ni la API key del proveedor LLM, que no debe exponerse al navegador (ACO-028). En particular, ninguna variable `VITE_*` (que Vite incrusta en el código que llega al navegador) contiene secretos.
- No se implementa autenticación propia: la identidad la gestiona Keycloak (ADR-011), y su integración es de ACO-018.
- Solo se añaden las dependencias nombradas a continuación.
- El servicio `frontend` no modifica los servicios `postgres` ni `backend` de `docker-compose.yml`, y el job `frontend` no modifica el job `backend` de la CI.
- `.gitignore` ya excluye `node_modules/`, `dist/`, `build/` y los `.env` locales; no hace falta cambiarlo.

### Dependencias nombradas

Herramientas y librerías del frontend React, que ya forma parte del stack. No añaden, retiran ni sustituyen ningún componente del stack.

- Aplicación: `react` y `react-dom` 19 (P12).
- Arranque y compilación: `vite`, `@vitejs/plugin-react`, `typescript` 6.0, `@types/react` y `@types/react-dom` (P1, B3).

- Estilo: `eslint`, `@eslint/js`, `typescript-eslint`, `eslint-plugin-react-hooks`, `eslint-plugin-react-refresh` y `globals` (P9).

## 10. Criterios de aceptación

### AC-01 — La aplicación arranca en Docker

Con `docker compose up -d --build` en un equipo sin Node instalado, `docker compose ps` muestra el servicio `frontend` en ejecución y `curl -s http://localhost:5173` devuelve HTML con el elemento raíz de la aplicación.

### AC-02 — La aplicación pinta su contenido

Al abrir `http://localhost:5173` se ve el nombre ACOMPAS, y la prueba de AC-04 lo comprueba de forma automática.

### AC-03 — Versión de Node fijada

El Dockerfile, `engines.node` de `package.json` y `frontend/.nvmrc` indican la misma versión de Node 24 (P2), y la CI la toma de `frontend/.nvmrc`.

### AC-04 — Prueba mínima con Vitest

`docker compose exec frontend npm test` ejecuta `src/App.test.tsx`, que monta `App` y comprueba que el texto ACOMPAS está en el documento, y termina con éxito. La prueba no necesita red ni el backend.

### AC-05 — Tipos y estilo

`docker compose exec frontend npm run typecheck` y `docker compose exec frontend npm run lint` terminan sin errores.

### AC-06 — CI

El job `frontend` de la CI ejecuta `npm ci`, `npm run lint`, `npm run typecheck` y `npm test`, y está en verde en la PR. El job `backend` sigue en verde.

### AC-07 — Preparada para móvil

`index.html` contiene la etiqueta `viewport` y `lang="es"` de P10.

### AC-08 — Instalación reproducible

`frontend/package-lock.json` está en el repositorio y la CI instala con `npm ci`.

### AC-09 — Sin secretos

No hay en `frontend/` ningún `.env` con valores ni ninguna variable `VITE_*` con secretos (inspección).

### AC-10 — Documentación

`README.md` y `README.es.md` indican cómo acceder al frontend y cómo ejecutar sus comprobaciones dentro del contenedor.

### AC-11 — Alcance

El PR solo modifica los componentes de la sección 12.

## 11. Tests esperados

Como mínimo:

1. `src/App.test.tsx`: monta `App` con Testing Library sobre `jsdom` y comprueba que aparece ACOMPAS (P7).
2. Comprobación de tipos y de estilo en la CI (P8).
3. Los tests del backend siguen pasando.

Los tests deben pasar sin red, sin el backend y sin navegador. Las pruebas con navegador no forman parte de este ACO (P7).

## 12. Componentes esperados

La implementación debe limitarse a:

- `frontend/` (incluida la eliminación de `frontend/.gitkeep`);
- `docker-compose.yml`, solo para añadir el servicio `frontend`;
- `.env.example`, solo para añadir `FRONTEND_PORT`;
- `.github/workflows/ci.yml`, solo para añadir el job `frontend`;
- `README.md` y `README.es.md`, solo la sección del entorno de desarrollo;
- `docs/aco/ACO-016.md` (esta ficha).

Si hiciera falta modificar cualquier otro archivo, el agente debe detenerse antes de hacerlo.
