## 1. Identificación

- **ID:** ACO-018
- **Nombre:** Login

El responsable, el soporte y la revisión, la estimación y las dependencias de este ACO son los de la matriz operativa del Documento Operativo del sprint en curso, que es su fuente única. Esta ficha no los repite.

## 2. Objetivo

Implementar el login del frontend mediante el mecanismo de identidad definido en Keycloak.

## 3. Incluye

1. Pantalla de login montada sobre `AuthShell`, con un botón que inicia el flujo OIDC configurado en ACO-013. No hay formulario de credenciales ni autenticación paralela.
2. Procesamiento del callback en `/auth/callback` sin router y sin dependencias de routing.
3. Gestión de la sesión en el navegador: lectura del resultado de autenticación, renovación del token de acceso y cierre de sesión.
4. Tratamiento de los errores básicos de autenticación, sin exponer tokens, claims ni detalles internos.
5. Transición entre `AuthShell` y `AppShell`, y contenido del slot `account`.
6. Pruebas automáticas con la librería OIDC simulada y comprobaciones manuales documentadas.

## 4. Resultado esperado

- La aplicación muestra una pantalla de login dentro de `AuthShell`, con la marca «ACOMPAS», un título y un botón; no muestra campos de usuario ni contraseña.
- Al pulsar el botón, el navegador va al formulario de login de Keycloak con el `client_id`, la redirección, el PKCE y los scopes configurados.
- Al volver a `/auth/callback`, el código se canjea una sola vez, la URL se limpia a `/` y la aplicación muestra el `AppShell` autenticado.
- El slot `account` muestra el email del usuario y un botón de cierre de sesión; el contenido principal es neutro y no monta la conversación.
- `getAccessToken()` devuelve el token vigente, lo renueva con el refresh token cuando está a punto de caducar y devuelve `null` si no puede renovarlo.
- El cierre de sesión elimina primero la sesión local y después redirige al cierre de sesión de Keycloak con vuelta a `http://localhost:5173/`.
- Los errores de login, callback, renovación y logout se muestran con un mensaje legible y permiten volver a intentarlo, sin bucles.
- A 360 px no hay scroll horizontal y el botón, los estados y los errores son utilizables sin zoom; en escritorio el login sigue centrado.
- `npm run lint`, `npm run typecheck` y `npm test` terminan sin errores. Los tests no usan red ni Keycloak.
- No se añaden router, gestión de estado global, librerías de estilos ni dependencias distintas de la nombrada en P1.
- No se modifican `AuthShell`, `AppShell`, el layout, el backend, el realm, Compose, los scripts ni la CI.

## 7. Restricciones técnicas

- React y TypeScript en modo estricto sobre Vite, con los componentes y estilos existentes.
- La única dependencia runtime nueva es `oidc-client-ts` (P1). No se añaden router, librería de estado, librería de estilos ni dependencias de test.
- Los tests usan Vitest, `jsdom` y Testing Library, ya presentes. No usan red, Keycloak, modelos ni servicios externos; la librería OIDC se simula.
- Los textos visibles están en español y «ACOMPAS» se escribe siempre en mayúsculas.
- No se usan datos reales de pacientes. No se persisten tokens ni claims en el servidor, en `localStorage` ni en cookies.
- No se guardan secretos en Git. El cliente es público y no tiene secreto.

- El access token dura 300 s; la sesión SSO inactiva dura 1800 s y la máxima, 36000 s. La renovación usa el refresh token, sin iframe ni `silent_redirect_uri`.
- Se usa `http://localhost:5173` de forma exacta. El acceso por `127.0.0.1` no coincide con la redirección registrada.
- No se modifican `frontend/src/components/layout/`, `frontend/src/main.tsx`, `frontend/vite.config.ts`, `frontend/package.json` más allá de la dependencia P1, el backend, `docker-compose.yml`, `infra/keycloak/`, `scripts/` ni `.github/workflows/ci.yml`.

## 8. Contrato de autenticación

| Campo | Valor | Origen |
| --- | --- | --- |
| `authority` | `http://localhost:8080/realms/acompas` | ACO-012/ACO-013 |
| `client_id` | `acompas-frontend` | ACO-013 |
| `redirect_uri` | `http://localhost:5173/auth/callback` | ACO-013 |
| `post_logout_redirect_uri` | `http://localhost:5173/` | ACO-013 |
| `scope` | `openid profile email roles` | ACO-013 |
| Ruta de callback | `/auth/callback` | ACO-013; P2 |

| `monitorSession` | `false` | P3; sin iframe |

La configuración vive en `authConfig.ts` y no se lee de variables de entorno. Cambiar el puerto del frontend o de Keycloak exige actualizar ACO-013 y esta configuración; no se hace en este ACO.

### 8.2 Estados de la interfaz

| Estado | Qué se muestra | Acciones |
| --- | --- | --- |
| Comprobando sesión | `AuthShell` con un aviso de carga (`role="status"`) | Ninguna |
| Anónimo | `AuthShell` con el login y el botón «Iniciar sesión» | Iniciar sesión |
| Redirigiendo | El mismo login, con el botón deshabilitado y `aria-busy` | Ninguna |
| Error | El login con un aviso `role="alert"` y el botón para reintentar | Iniciar sesión |
| Autenticado | `AppShell` con nav, contenido neutro y `account` con email y logout | Cerrar sesión |

### 8.3 Callback sin router

1. Al arrancar, si `window.location.pathname` es `/auth/callback`, se llama al servicio de callback.
2. El servicio memoiza el canje por URL. Dos efectos de `StrictMode` o un remontaje reutilizan la misma promesa y no canjean el código dos veces.
3. Al terminar, tanto en éxito como en error, el servicio limpia la URL a `/` con `history.replaceState`.
4. Si el canje falla, se muestra el error en el login y se ofrece reintentar iniciando un flujo nuevo. No se reintenta automáticamente el mismo código, que es de un solo uso.
5. Si el canje funciona, el usuario queda autenticado y se muestra el `AppShell`.

### 8.4 Token y contrato con ACO-019

- `getAccessToken(): Promise<string | null>` es la función que consume ACO-019.
- Devuelve el `access_token` si sigue vigente.
- Si al token le quedan 30 s o menos, intenta renovarlo con `signinSilent()`, que usa el refresh token.
- Si no hay refresh token o la renovación falla, elimina la sesión local y devuelve `null`.
- ACO-019 debe llamar a `getAccessToken()` antes de cada petición y tratar `null` como sesión no válida, volviendo al login.
- No se usa iframe, `silent_redirect_uri` ni renovación automática en segundo plano.

### 8.5 Errores

| Situación | Mensaje | Qué hace la interfaz |
| --- | --- | --- |
| Falla el inicio de la redirección | «No se ha podido iniciar la sesión. Inténtalo de nuevo.» | Mantiene el login y permite reintentar |
| Falla el callback o el canje | «No se ha podido completar el inicio de sesión. Inténtalo de nuevo.» | Limpia la URL a `/` y muestra el login |
| Falla la renovación | No se muestra un error técnico | Elimina la sesión y devuelve `null` a ACO-019 |
| Falla el logout remoto | «No se ha podido cerrar la sesión en Keycloak.» | La sesión local ya está eliminada; muestra el login |

Los mensajes no incluyen el token, sus claims, la URL del proveedor ni el detalle de la librería. Tampoco se escriben en logs.

### 8.6 Transición y cuenta

- Sin sesión: `AuthShell` + `LoginPage`.
- Con sesión: `AppShell` con el `navItems` existente (`conversation`, «Conversación»), `activeNavId="conversation"`, `account` con el email y el botón de logout, y `children` neutro.
- No se monta `ConversationPage` ni se modifica el layout.
- Si el perfil no trae email, el slot muestra «Sesión iniciada».

## 10. Criterios de aceptación

### AC-01 — Login sin credenciales

La pantalla de login usa `AuthShell`, muestra «ACOMPAS», el título «Iniciar sesión» y un botón. No hay formulario de credenciales, campos de usuario o contraseña, cabecera, navegación, pie ni disclaimer. La prueba lo comprueba.

### AC-02 — Redirección a Keycloak

Al pulsar el botón se llama una sola vez a la redirección OIDC. Mientras se redirige, el botón queda deshabilitado y con estado de espera. Si la redirección falla, se muestra un error legible con `role="alert"` y se permite reintentar. La prueba usa un espía.

### AC-03 — Callback sin router ni duplicados

En `/auth/callback` se procesa el callback una sola vez, incluso con `StrictMode` o un remontaje; se canjea el código, se limpia la URL a `/` y se muestra la aplicación autenticada. Si el callback falla, se limpia la URL, se muestra un error y se permite iniciar un flujo nuevo sin bucles. No se importa ningún router.

### AC-04 — Sesión y transición

Sin sesión se muestra `AuthShell` con el login. Con sesión se muestra `AppShell`, el email en `account`, el botón de logout y el contenido neutro. Durante la comprobación inicial se muestra el estado de carga. La prueba cubre los tres estados.

### AC-05 — Renovación

`getAccessToken()` devuelve el token vigente. Con 30 s o menos de vida, renueva con `signinSilent()` usando el refresh token. Si no hay refresh token o la renovación falla, elimina la sesión y devuelve `null`. No se configura `silent_redirect_uri` ni se usa iframe. La prueba cubre token vigente, 31 s, 29 s, sin refresh y renovación fallida.

### AC-06 — Logout

El logout captura el `id_token`, elimina primero la sesión local y después llama a `signoutRedirect` con `post_logout_redirect_uri = http://localhost:5173/`. Si el logout remoto falla, la sesión local ya está eliminada y se muestra el login. La prueba comprueba el orden de las llamadas y el valor de la URI.

### AC-07 — Contrato con ACO-019 y sin estado global

`getAccessToken()` está exportado y documentado como contrato para ACO-019, que debe llamarlo antes de cada petición y tratar `null` como sesión no válida. No se introduce router, contexto global ni librería de estado. No se registran tokens ni claims.

### AC-08 — Criterio móvil

A 360 px no hay scroll horizontal, el botón, los estados y los errores son legibles y utilizables sin zoom, y el login se mantiene centrado. En escritorio se mantiene el centrado de `AuthShell`. La comprobación es manual; los tests cubren estructura, estados y llamadas.

### AC-09 — Alcance

El PR solo modifica los archivos de la lista «Componentes esperados» de esta ficha. `AuthShell`, `AppShell`, el layout, `main.tsx`, `vite.config.ts`, el backend, el realm, Compose, los scripts y la CI no cambian.

### AC-10 — Seguridad y datos

No hay datos reales de pacientes, secretos ni persistencia en servidor. Los tokens solo viven en `sessionStorage`; no se usan `localStorage`, cookies ni logs. El cliente es público y no tiene secreto. La comprobación manual no crea usuarios en el realm.

### AC-11 — Comprobaciones y CI

`npm run lint`, `npm run typecheck` y `npm test` terminan sin errores y sin red. El job `frontend` de la CI sigue ejecutando lint, typecheck y test y queda en verde. La comprobación manual M1 (llegada al formulario de Keycloak) y M2 (layout a 360 px y 1280 px) se documentan en la PR. M3 (login completo con usuario sintético y 2FA) queda documentada y pendiente de ACO-015.
