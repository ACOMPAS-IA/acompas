## 1. Identificación

- **ID:** ACO-011
- **Nombre:** Keycloak local

El responsable, el soporte y la revisión, la estimación y las dependencias de este ACO son los de la matriz operativa del Documento Operativo del sprint en curso, que es su fuente única. Esta ficha no los repite.

## 2. Objetivo

Instalar y dejar disponible Keycloak en el entorno local de desarrollo.

## 3. Incluye

1. Keycloak ejecutable localmente: un servicio `keycloak` en `docker-compose.yml` que arranca con `docker compose up -d` junto a los servicios existentes (según P1, P2, P3 y P4).
2. Configuración reproducible para el equipo:
   - versión de la imagen fijada (P1);
   - credenciales de administrador inicial configurables por entorno, sin secretos en Git (P5);
   - comprobación de salud en Compose (P7);
   - script de comprobación (P8);
   - documentación de arranque en los README (P9).
3. Base preparada para el realm de ACO-012: directorio de importación montado y arranque con importación activada, sin ningún realm propio todavía (P6).

## 4. Resultado esperado

Tras `cp .env.example .env` y `docker compose up -d`, en cualquier equipo del equipo:

- el servicio `keycloak` aparece en `docker compose ps` como `healthy`;
- la consola de administración responde en `http://localhost:8080` (o el puerto de `KEYCLOAK_PORT`);
- `http://localhost:8080/realms/master/.well-known/openid-configuration` devuelve el documento de descubrimiento OIDC;
- se puede entrar en la consola con las credenciales de administrador definidas en `.env`;
- el único realm existente es `master`;
- los datos de Keycloak sobreviven a `docker compose down` y `up`, y desaparecen al borrar su volumen;
- el backend y PostgreSQL siguen arrancando como antes.

## 5. Fuera de alcance

No forman parte de ACO-011:

- el realm de ACOMPAS, sus clientes, roles, usuarios, 2FA y política de contraseñas (ACO-012);
- el flujo OAuth2/OIDC de la aplicación y el login verificable (ACO-013);
- la validación de JWT en el backend y cualquier variable o dependencia del backend hacia Keycloak (ACO-014);
- la lista blanca del piloto (ACO-015);
- el login del frontend (ACO-018);
- el despliegue de Keycloak fuera del entorno local: modo `start`, TLS, almacenamiento de producción, copias de seguridad e infraestructura (ADR-011, fuera de esta decisión);
- el uso de la Admin API de Keycloak (ADR-001, fuera de esta decisión);
- cambios en la CI (P8);
- usuarios de prueba de cualquier tipo.

## 6. Relación con otros ACO

Las dependencias de este ACO se consultan en la matriz operativa del Documento Operativo del sprint en curso.

Este ACO entrega a los siguientes:

- **ACO-012:** un Keycloak local en marcha y el directorio `infra/keycloak/import/`, cuyo contenido se importa al arrancar (P6). ACO-012 crea ahí el realm de ACOMPAS.
- **ACO-013 y ACO-014:** la URL base de Keycloak en local (`http://localhost:8080`, o `http://keycloak:8080` desde la red de Compose) y un servicio con `healthcheck` del que pueden depender.

## 7. Restricciones técnicas

- Keycloak self-hosted es el proveedor de identidad de ACOMPAS (ADR-011). Este ACO solo lo levanta en local.
- Keycloak es el custodio de la correspondencia email↔UUID; ACOMPAS no almacena el email (ADR-001). Por eso este ACO no conecta Keycloak con la base de datos de ACOMPAS (P3).
- PostgreSQL es la única base de datos de aplicación (ADR-007); ver P3.
- Las credenciales y los secretos no se guardan en Git (AGENTS.md §7). `.env` ya está en `.gitignore`.
- No se añaden dependencias Python ni de frontend.
- El entorno de referencia es Docker Compose (`README.es.md`).

## 9. Comprobación de salud

Según P7, el `healthcheck` del servicio `keycloak` en `docker-compose.yml` es:

```yaml
healthcheck:
  test:
    - CMD
    - bash
    - -c
    - >-
      exec 3<>/dev/tcp/127.0.0.1/9000 &&
      printf 'GET /health/ready HTTP/1.1\r\nHost: localhost\r\nConnection: close\r\n\r\n' >&3 &&
      read -r status <&3 &&
      [[ $status == *' 200 '* ]]
  interval: 10s
  timeout: 5s
  retries: 12
  start_period: 30s
```

- Abre una conexión TCP con el puerto de gestión dentro del propio contenedor; si Keycloak no escucha, `exec` falla y la comprobación también.
- Lee solo la línea de estado de la respuesta y exige el código `200`. Usa solo funciones internas de `bash`, sin depender de `head`, `grep` ni otras utilidades de la imagen.
- `/health/ready` solo existe con `KC_HEALTH_ENABLED=true`.

## 10. Datos de prueba

Está prohibido utilizar datos reales de pacientes, también como punto de partida (ADR-008).

Este ACO no crea usuarios ni carga datos: el único usuario es el administrador inicial de Keycloak, con credenciales de desarrollo. No se usan emails reales.

## 11. Criterios de aceptación

### AC-01 — Configuración válida

`docker compose config` termina sin errores y muestra el servicio `keycloak` con la imagen de versión fijada (rama 26 o posterior), el puerto publicado en `127.0.0.1`, el volumen `keycloak_data`, el montaje de `infra/keycloak/import/`, el `healthcheck` de la sección 9 y las variables `KC_BOOTSTRAP_ADMIN_USERNAME` y `KC_BOOTSTRAP_ADMIN_PASSWORD`.

### AC-02 — Keycloak arranca y está sano

Con un `.env` copiado de `.env.example`, `docker compose up -d` deja el servicio `keycloak` en estado `healthy` según `docker compose ps`.

### AC-03 — Endpoint OIDC disponible

`curl -fsS http://localhost:8080/realms/master/.well-known/openid-configuration` devuelve un JSON cuyo `issuer` es `http://localhost:8080/realms/master`.

### AC-04 — Puerto solo en local

`docker compose port keycloak 8080` devuelve `127.0.0.1:8080` (o el puerto de `KEYCLOAK_PORT`), no `0.0.0.0`. El puerto 9000 no está publicado.

### AC-05 — Acceso de administración

Se puede iniciar sesión en la consola de administración con los valores de `KEYCLOAK_BOOTSTRAP_ADMIN_USER` y `KEYCLOAK_BOOTSTRAP_ADMIN_PASSWORD` del `.env`. Cambiar esos valores en `.env` antes del primer arranque cambia las credenciales.

### AC-06 — Sin realm propio

Tras el arranque, el único realm es `master`. `infra/keycloak/import/` solo contiene `.gitkeep`.

### AC-07 — Persistencia local

Un cambio hecho en la consola (por ejemplo, el nombre visible del realm `master`) se conserva tras `docker compose down` y `docker compose up -d`, y desaparece tras `docker compose down` y borrar el volumen `keycloak_data`.

### AC-08 — Sin regresiones

Con Keycloak en marcha, `curl http://localhost:8000/health` sigue devolviendo `{"status":"ok"}` y `pytest` del backend pasa.

### AC-09 — Sin secretos en Git

El PR no contiene credenciales fuera de los valores por defecto de desarrollo aceptados en P5, ni ficheros `.env`.

### AC-10 — Script de comprobación

`scripts/check-keycloak.sh` termina con código 0 con Keycloak en marcha y distinto de 0 con Keycloak parado.

### AC-11 — Documentación

`README.es.md` y `README.md` explican cómo arrancar Keycloak, la URL de la consola, de dónde salen las credenciales y cómo borrar su volumen.

### AC-12 — Alcance

El PR solo modifica los componentes de la sección 13.

## 12. Tests esperados

Como mínimo:

1. `docker compose config` sin errores (AC-01).
2. `scripts/check-keycloak.sh` con Keycloak en marcha y parado (AC-02, AC-03, AC-10).
