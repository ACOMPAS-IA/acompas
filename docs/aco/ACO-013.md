## 1. Identificación

- **ID:** ACO-013
- **Nombre:** OAuth2/OIDC

El responsable, el soporte y la revisión, la estimación y las dependencias de este ACO son los de la matriz operativa del Documento Operativo del sprint en curso, que es su fuente única. Esta ficha no los repite.

## 2. Objetivo

Configurar el mecanismo de autenticación OAuth2/OIDC sobre Keycloak para ACOMPAS.

## 3. Incluye

1. Cliente OIDC de la aplicación en el realm `acompas`: `acompas-frontend`, público, authorization code con PKCE `S256`, URI de redirección, origen web y scopes de desarrollo (P1–P3, P5).
2. Verificación local del mecanismo: descubrimiento OIDC, metadatos del cliente y petición de autorización hasta el formulario de login, sin usuarios ni credenciales (P4, P6).
3. Configuración documentada para la integración posterior: `infra/keycloak/README.md` (P7).
4. Comprobación reproducible: `scripts/check-realm.sh` ampliado (P6).

## 4. Resultado esperado

Con Keycloak en marcha y el realm reconstruido desde el JSON:

- `GET /admin/realms/acompas/clients?clientId=acompas-frontend` devuelve un único cliente con `publicClient: true`, `standardFlowEnabled: true`, `implicitFlowEnabled: false`, `directAccessGrantsEnabled: false`, `serviceAccountsEnabled: false`, `protocol: openid-connect`, la redirección `http://localhost:5173/auth/callback`, el origen `http://localhost:5173`, `pkce.code.challenge.method` igual a `S256`, `fullScopeAllowed: true` y los scopes por defecto de la sección 8.
- El cliente no tiene secreto.
- Una petición a `/realms/acompas/protocol/openid-connect/auth` con `client_id=acompas-frontend`, la redirección registrada, `response_type=code`, `scope=openid`, `state` y `code_challenge` con método `S256` devuelve el formulario de login de Keycloak.
- La misma petición con una redirección no registrada se rechaza y no muestra el formulario.
- El JSON no contiene usuarios, credenciales ni secretos de cliente; `acompas-frontend` no tiene secreto y el realm sigue sin usuarios.
- `scripts/check-realm.sh` termina con código 0 y falla si el cliente falta o no coincide.
- `infra/keycloak/README.md` describe el cliente y su comprobación.
- El backend, el frontend y la CI no cambian.

## 5. Fuera de alcance

No forman parte de ACO-013:

- la validación del JWT y de sus claims en el backend (ACO-014);
- el alta de usuarios, la lista blanca y la resolución email↔UUID (ACO-015; ADR-009);
- el login del frontend, el refresco de token y el cierre de sesión en el navegador (ACO-018);
- el cliente de API del frontend (ACO-019);
- el flujo extremo a extremo y sus pruebas (ACO-032 y ACO-033);
- crear usuarios, credenciales o usuarios de prueba en el realm (ACO-012 P2; ADR-009);
- añadir librerías OIDC o cualquier dependencia: una dependencia nueva es decisión conjunta y el login es de ACO-018;
- cambiar el realm más allá del cliente: roles, 2FA, políticas o flujos (ACO-012);
- TLS, `KC_HOSTNAME`, producción y despliegue (ACO-011; ADR-011);
- un job de CI para Keycloak (ACO-012 P12);
- cambios en `docker-compose.yml`, en `scripts/check-keycloak.sh` o en la CI.

## 6. Relación con otros ACO

Las dependencias de este ACO se consultan en la matriz operativa del Documento Operativo del sprint en curso.

ACO-012 entrega a este ACO el realm `acompas`, su issuer, los roles `paciente` y `administrador` y el mecanismo de importación. ACO-013 añade el cliente OIDC al mismo JSON.

Este ACO entrega a los siguientes:

- **ACO-014:** el issuer, el `client_id` `acompas-frontend` y los claims que llevará el token (`sub` con el UUID, `email` y `realm_access.roles`). ACO-014 decide qué claims valida y si necesita un mapper de audiencia; añadirlo sería un cambio de esta ficha.
- **ACO-015:** un cliente que ya puede autenticar usuarios; el alta y la lista blanca siguen siendo suyos.
- **ACO-018:** el `client_id`, el flujo con PKCE, la redirección `http://localhost:5173/auth/callback` y el origen web. ACO-018 implementa la ruta y decide su librería.
- **ACO-019 y ACO-032:** el token obtenido por ACO-018 y el contrato de autorización que consumen.

## 7. Restricciones técnicas

- Keycloak 26.8.0, la versión fijada en `docker-compose.yml` (ACO-011).
- El cliente se declara en el JSON de importación de Keycloak 26 (ACO-012).
- Cliente público sin secreto; PKCE `S256` obligatorio (P1, P3).
- No se guardan secretos, credenciales ni usuarios en el JSON (ACO-012 §7; ADR-008).
- No se usan datos reales (ADR-008).
- Keycloak sigue siendo el único custodio de la correspondencia email↔UUID; ACOMPAS no la almacena (ADR-001).
- La lista blanca no se implementa en Keycloak (ADR-009).
- Las duraciones de token son las de ACO-012 P8: acceso 300 s, sesión SSO inactiva 1800 s y máxima 36000 s. El refresco y el cierre de sesión en el navegador son de ACO-018.
- Sin dependencias nuevas y sin cambios en la CI (P6; §5).
- Solo entorno local, HTTP en `localhost`, sin TLS, sin `KC_HOSTNAME` y sin configuración de producción (ACO-011).
- El realm no contiene usuarios (ACO-012 P2; ADR-009).

## 9. Datos de prueba

Está prohibido utilizar datos reales de pacientes, también como punto de partida (ADR-008).

No se crean usuarios. Las comprobaciones usan solo peticiones HTTP sin credenciales:

- `state` y `code_challenge` sintéticos, generados por el script;
- una redirección no registrada, para el caso negativo;
- ningún nombre, email ni identificador de persona.

## 10. Criterios de aceptación

### AC-01 — Cliente OIDC

Tras reimportar el realm, la Admin API devuelve el cliente `acompas-frontend` con los valores de la sección 8: público, authorization code, sin flujo implícito, sin concesión directa, sin cuenta de servicio, con PKCE `S256`, la redirección y el origen registrados, los scopes por defecto declarados, `fullScopeAllowed: true` y sin secreto.

### AC-02 — Petición de autorización

Una petición de autorización con el cliente y la redirección registrados devuelve el formulario de login de Keycloak. Con una redirección no registrada, Keycloak rechaza la petición y no muestra el formulario.

### AC-03 — Sin usuarios ni secretos en el JSON y en el cliente

El JSON no contiene usuarios, credenciales ni secretos de cliente. El cliente `acompas-frontend` es público y no tiene secreto. Tras la importación, el realm sigue sin usuarios. No se comprueba el resto de clientes integrados de Keycloak, que no son de este ACO.

### AC-04 — Scopes y claims

El cliente declara los scopes de la sección 8 y `fullScopeAllowed: true`, y no se añaden mappers ni claims propios. La comprobación de los claims con un token real corresponde a ACO-014, que dispondrá de usuarios creados por ACO-015.

### AC-05 — Documentación

`infra/keycloak/README.md` describe el cliente, el flujo con PKCE, las URI, los scopes, la reimportación y la comprobación.

### AC-06 — Comprobación

`scripts/check-realm.sh` termina con código 0 con Keycloak en marcha y falla si el cliente no existe o no coincide con la sección 8. No imprime el token ni la contraseña.

### AC-07 — Alcance

El PR solo modifica los componentes de la sección 12.

### AC-08 — Sin datos reales

Los tests, el JSON y la documentación solo contienen valores sintéticos (ADR-008).

### AC-09 — Sin cambios colaterales

El backend, el frontend, `docker-compose.yml`, `scripts/check-keycloak.sh` y la CI no cambian. Los tests existentes siguen pasando.

## 11. Tests esperados

Como mínimo:

1. Importación desde un volumen vacío: el cliente aparece con los valores de la sección 8 (AC-01).
2. `scripts/check-realm.sh`: descubrimiento, cliente por la Admin API y petición de autorización con el formulario de login (AC-02, AC-06).
3. Caso negativo: cliente inexistente o redirección no registrada, rechazados (AC-02, AC-06).
4. JSON sin usuarios ni secretos (AC-03).
5. Documentación con los valores del cliente (AC-05).
6. Los tests de backend y frontend siguen pasando (AC-09).

Las comprobaciones 1 a 5 necesitan Keycloak local; no usan red externa, modelo ni datos reales. No se añade un job de CI: la CI actual no levanta Keycloak (ACO-012 P12).
