## 1. Identificación

- **ID:** ACO-017
- **Nombre:** Layout

El responsable, el soporte y la revisión, la estimación y las dependencias de este ACO son los de la matriz operativa del Documento Operativo del sprint en curso, que es su fuente única. Esta ficha no los repite.

## 2. Objetivo

Implementar el layout mínimo de la aplicación necesario para el flujo de Sprint 1.

## 3. Incluye

1. Un `AppShell` con cabecera, navegación, zona principal desplazable y pie permanente de disclaimer, preparado para montar las pantallas del Sprint 1.
2. Un `AuthShell` para la pantalla de login, sin las regiones del marco autenticado.
3. El contrato de navegación y de slots que utilizarán los ACO posteriores.
4. Los estilos mínimos del layout, mobile-first, con un breakpoint `min-width`, sin JavaScript y con el pie de disclaimer siempre visible.
5. Las pruebas y comprobaciones del layout.

No se construyen en este ACO las pantallas de login, subida de documento ni conversación: solo el marco donde se montarán.

## 4. Resultado esperado

- `AppShell` renderiza una cabecera con «ACOMPAS», una región de navegación, una zona principal para `children` y un pie permanente para el disclaimer.
- Si el slot `disclaimer` está vacío, el pie no se muestra.
- `AuthShell` renderiza un `<main>` centrado con «ACOMPAS» y `children`, sin cabecera, navegación, pie ni disclaimer.
- La navegación pinta los `navItems`, marca el ítem activo y notifica `onNavigate(id)` sin cambiar de pantalla.
- `App` muestra el `AppShell` con contenido neutro y un único ítem, «Conversación».
- La zona principal es la única que se desplaza; el pie de disclaimer permanece visible y no tapa el contenido.
- Los estilos son CSS sin JavaScript; el layout es mobile-first y cumple el criterio de aceptación móvil de P4 y el pie permanente de P5 a 360 px y 1280 px.
- Dentro del contenedor, `npm run lint`, `npm run typecheck` y `npm test` terminan sin errores.
- El job `frontend` de la CI ejecuta lint, typecheck y test y está en verde.
- La aplicación arranca en Docker y sirve HTML en el puerto del frontend.
- No se añaden dependencias, router, gestión de estado ni pantallas reales.

## 5. Fuera de alcance

No forman parte de ACO-017:

- Login y autenticación con Keycloak (ACO-018).
- Cliente del API backend, proxy y CORS (ACO-019).
- Contenido y comportamiento de la conversación (ACO-030).
- Texto, lógica y condiciones del disclaimer (ACO-031).
- Pantallas de subida y validación de documentos (su ACO correspondiente).
- Router, gestión de estado y bibliotecas de componentes o estilos.
- Script `build`, build de producción de Vite, cambios en la CI y servicio de producción del frontend.
- Aplicaciones nativas, publicación en tiendas y PWA (manifest, service worker e iconos). La PWA se evalúa en otro ACO o decisión.
- Datos reales de pacientes, persistencia y secretos.

## 6. Relación con otros ACO

Las dependencias de este ACO se consultan en la matriz operativa del Documento Operativo del sprint en curso.

- **ACO-018 (Login)** usa `AuthShell` para montar el formulario y decide la transición a `AppShell` tras autenticar.
- **ACO-030 (Conversación)** monta su pantalla como `children` de `AppShell` y puede proporcionar `navItems`, `activeNavId` y `onNavigate`.
- **ACO-031 (Disclaimer)** define el contenido y el comportamiento del disclaimer de `AppShell`; `AuthShell` no lo incluye. ACO-017 garantiza que el pie sea permanente.

## 7. Restricciones técnicas

- La implementación se limita al frontend, a React y TypeScript en modo estricto y a Vite.
- No se añaden dependencias, router, gestión de estado, bibliotecas de componentes ni CSS-in-JS.
- La base CSS es móvil; el breakpoint se expresa con `min-width`.
- No se hacen llamadas al backend ni se implementa autenticación.
- Las pruebas usan Vitest, `jsdom` y Testing Library, ya presentes en las devDependencies; el entorno DOM ya está configurado en `vite.config.ts`. No se añade ninguna librería.
- Los textos visibles están en español y «ACOMPAS» se escribe siempre en mayúsculas.
- No se usan datos reales de pacientes ni se persiste información.

- No se modifica `frontend/package.json`, `frontend/package-lock.json`, `frontend/vite.config.ts` ni `.github/workflows/ci.yml`.

## 8. Contrato de composición

### `NavItem`

- `id`: identificador estable y único de la sección. Es el valor que recibe `onNavigate`.
- `label`: texto visible en español.

### `AppShell`

- `navItems`: lista de `NavItem` que se pinta en la región de navegación.
- `activeNavId`: `id` del ítem activo. Si coincide con un `NavItem.id`, ese ítem recibe `aria-current="page"`; si no coincide, ninguno está activo.
- `onNavigate`: función opcional que recibe el `id` del ítem activado. No recibe el evento y no cambia de pantalla. Si no se proporciona, el ítem se muestra pero no navega.
- `account`: slot `ReactNode` de la cabecera para la identidad o la cuenta. Vacío por defecto; lo rellena ACO-018.
- `disclaimer`: slot `ReactNode` del pie para el aviso legal. Vacío por defecto; lo rellena ACO-031. El pie es permanente: el layout mantiene la altura del viewport y solo desplaza la zona principal. Si el slot está vacío, el pie no se muestra.
- `children`: contenido de la zona principal.

La estructura semántica es:

- `<header>` con un `h1` «ACOMPAS» y el slot `account`.
- `<nav aria-label="Navegación principal">` con los ítems como botones.
- `<main>` con `children`.
- `<footer aria-label="Aviso legal">` con el slot `disclaimer`.

Los ítems de navegación son botones, no enlaces: no hay router ni URL asociada.

### `AuthShell`

- `children`: contenido de la pantalla de login.
- Renderiza un `<main>` centrado con la marca «ACOMPAS» y `children`.
- No renderiza cabecera, navegación, pie ni disclaimer.

### `App`

- Renderiza `AppShell` con un único `NavItem` de `id` `conversation` y etiqueta «Conversación».
- Marca ese ítem como activo.
- Usa un contenido neutro en `children`; no monta login, conversación ni disclaimer reales.

## 9. Datos de prueba

Está prohibido utilizar datos reales de pacientes, también como punto de partida (ADR-008).

Este ACO no maneja datos de pacientes. Las pruebas usan textos sintéticos como «Contenido de prueba» y «Conversación»; no hay persistencia ni llamadas externas.

## 10. Criterios de aceptación

### AC-01 — `AppShell` y sus regiones

`AppShell` renderiza una cabecera con «ACOMPAS» y el slot `account`, una navegación accesible, una zona principal con `children` y un pie con el slot `disclaimer`. El pie se muestra cuando el slot tiene contenido y no se muestra si está vacío. La prueba comprueba las regiones y que cada slot aparece en su lugar.

### AC-02 — `AuthShell`

`AuthShell` renderiza un `<main>` centrado con «ACOMPAS» y `children`, y no renderiza cabecera, navegación, pie ni disclaimer. La prueba lo comprueba.

### AC-03 — Contrato de navegación

`AppShell` pinta los `navItems`, marca con `aria-current="page"` el que coincide con `activeNavId` y llama a `onNavigate` con el `id` del ítem activado. No hay router ni cambio de pantalla. La prueba usa un espía para comprobar el argumento.

### AC-04 — `App` de demostración

`App` monta `AppShell` con el ítem «Conversación» y contenido neutro. No monta el formulario de login, la conversación ni el texto del disclaimer, y el pie no se muestra. La prueba lo comprueba.

### AC-05 — Sin dependencias ni router

`frontend/package.json` y `frontend/package-lock.json` no cambian, no se importa ningún router ni biblioteca de estado o estilos, y el layout solo usa React y CSS. Se comprueba con la inspección del diff y de los imports.

### AC-06 — Comprobaciones y arranque

Dentro del contenedor:

- `npm run lint` termina sin errores.
- `npm run typecheck` termina sin errores.
- `npm test` termina sin errores y sin red.

En el host:

- `docker compose up -d --build frontend` reconstruye la imagen Docker, levanta el servicio y `curl -fsS http://127.0.0.1:5173/` devuelve HTML con el elemento raíz.

El build local de Vite con `docker compose exec frontend npm exec -- vite build` es una comprobación opcional y no forma parte de los criterios de aceptación. No confundirlo con `docker compose up -d --build frontend`, que construye la imagen Docker.

### AC-07 — CI

El job `frontend` de la CI ejecuta lint, typecheck y test y está en verde.

### AC-08 — Alcance

El PR solo modifica los archivos de la sección 12.

### AC-09 — Sin datos reales

No hay datos reales de pacientes, persistencia ni secretos en el código ni en las pruebas.

### AC-10 — Uso en móvil

A 360 px de ancho no hay scroll horizontal y la navegación, el contenido principal y el disclaimer son accesibles. A 1280 px se mantiene el layout amplio. La comprobación es manual en el navegador; no se añade una prueba E2E ni una dependencia.

### AC-11 — Pie de disclaimer permanente

Al desplazar la zona principal, el pie de disclaimer permanece visible y no tapa el contenido. Se comprueba a 360 px y 1280 px con un contenido de prueba que desborde la zona principal. La comprobación es manual; no se añade una prueba E2E ni una dependencia.

## 11. Tests esperados
