## 1. Identificación

- **ID:** ACO-017
- **Nombre:** Layout

El responsable, el soporte y la revisión, la estimación y las dependencias de este ACO son los de la matriz operativa del Documento Operativo del sprint en curso, que es su fuente única. Esta ficha no los repite.

## 2. Objetivo

Implementar el layout mínimo de la aplicación necesario para el flujo de Sprint 1.

## 3. Incluye

1. Un `AppShell` con cabecera, navegación, zona principal y hueco de disclaimer, preparado para montar las pantallas del Sprint 1.
2. Un `AuthShell` para la pantalla de login, sin las regiones del marco autenticado.
3. El contrato de navegación y de slots que utilizarán los ACO posteriores.
4. Los estilos mínimos del layout, con un único breakpoint y sin JavaScript.
5. Las pruebas y comprobaciones del layout.

No se construyen en este ACO las pantallas de login, subida de documento ni conversación: solo el marco donde se montarán.

## 4. Resultado esperado

- `AppShell` renderiza una cabecera con «ACOMPAS», una región de navegación, una zona principal para `children` y un pie para el disclaimer.
- `AuthShell` renderiza un contenedor centrado con «ACOMPAS» y `children`, sin cabecera, navegación ni pie.
- La navegación pinta los `navItems`, marca el ítem activo y notifica `onNavigate(id)` sin cambiar de pantalla.
- `App` muestra el `AppShell` con contenido neutro y un único ítem, «Conversación».
- Los estilos son CSS sin JavaScript; la adaptabilidad móvil queda limitada a P4 y no es criterio de aceptación.
- Dentro del contenedor, `npm run lint`, `npm run typecheck`, `npm test` y el build local terminan sin errores.
- La CI ejecuta lint, typecheck y test; queda pendiente que incorpore el build y cubra las mismas comprobaciones que los criterios.
- La aplicación arranca en Docker y sirve HTML en el puerto del frontend.
- No se añaden dependencias, router, gestión de estado ni pantallas reales.

## 8. Contrato de composición

### `NavItem`

- `id`: identificador estable y único de la sección. Es el valor que recibe `onNavigate`.
- `label`: texto visible en español.

### `AppShell`

- `navItems`: lista de `NavItem` que se pinta en la región de navegación.
- `activeNavId`: `id` del ítem activo. Si coincide con un `NavItem.id`, ese ítem recibe `aria-current="page"`; si no coincide, ninguno está activo.
- `onNavigate`: función opcional que recibe el `id` del ítem activado. No recibe el evento y no cambia de pantalla. Si no se proporciona, el ítem se muestra pero no navega.
- `account`: slot `ReactNode` de la cabecera para la identidad o la cuenta. Vacío por defecto; lo rellena ACO-018.
- `disclaimer`: slot `ReactNode` del pie para el aviso legal. Vacío por defecto; lo rellena ACO-031.
- `children`: contenido de la zona principal.

La estructura semántica es:

- `<header>` con un `h1` «ACOMPAS» y el slot `account`.
- `<nav aria-label="Navegación principal">` con los ítems como botones.
- `<main>` con `children`.
- `<footer aria-label="Aviso legal">` con el slot `disclaimer`.

Los ítems de navegación son botones, no enlaces: no hay router ni URL asociada.

### `AuthShell`

- `children`: contenido de la pantalla de login.
- Renderiza un contenedor centrado con la marca «ACOMPAS» y `children`.
- No renderiza cabecera, navegación ni pie.

### `App`

- Renderiza `AppShell` con un único `NavItem` de `id` `conversation` y etiqueta «Conversación».
- Marca ese ítem como activo.
- Usa un contenido neutro en `children`; no monta login, conversación ni disclaimer reales.

## 9. Datos de prueba

## 10. Criterios de aceptación

### AC-01 — `AppShell` y sus regiones

`AppShell` renderiza una cabecera con «ACOMPAS» y el slot `account`, una navegación accesible, una zona principal con `children` y un pie con el slot `disclaimer`. La prueba comprueba las regiones y que cada slot aparece en su lugar.

### AC-02 — `AuthShell`

`AuthShell` renderiza «ACOMPAS» y `children` en un contenedor centrado, y no renderiza cabecera, navegación ni pie. La prueba lo comprueba.

### AC-03 — Contrato de navegación

`AppShell` pinta los `navItems`, marca con `aria-current="page"` el que coincide con `activeNavId` y llama a `onNavigate` con el `id` del ítem activado. No hay router ni cambio de pantalla. La prueba usa un espía para comprobar el argumento.

### AC-04 — `App` de demostración

`App` monta `AppShell` con el ítem «Conversación» y contenido neutro. No monta el formulario de login, la conversación ni el texto del disclaimer. La prueba lo comprueba.

### AC-05 — Sin dependencias ni router

`frontend/package.json` y `frontend/package-lock.json` no cambian, no se importa ningún router ni biblioteca de estado o estilos, y el layout solo usa React y CSS. Se comprueba con la inspección del diff y de los imports.

### AC-06 — Comprobaciones y arranque

Dentro del contenedor:

- `npm run lint` termina sin errores.
- `npm run typecheck` termina sin errores.
- `npm test` termina sin errores y sin red.
- `npm exec -- vite build` termina sin errores.

En el host:

- `docker compose up -d --build frontend` levanta el servicio y `curl -fsS http://127.0.0.1:5173/` devuelve HTML con el elemento raíz.

### AC-07 — CI

El job `frontend` de la CI ejecuta `npm ci`, `npm run lint`, `npm run typecheck` y `npm test`, y está en verde. El build no forma parte del job actual: se verifica localmente y queda pendiente de la CI (HALLAZGO de ACO-016). Este criterio queda pendiente hasta que el job incorpore el build y ejecute las mismas comprobaciones que los criterios: lint, typecheck, test y build.

### AC-08 — Alcance

### AC-09 — Sin datos reales

No hay datos reales de pacientes, persistencia ni secretos en el código ni en las pruebas.
