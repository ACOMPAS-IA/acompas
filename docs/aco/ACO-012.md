# ACO-012 — Realm/configuración

> **Estado: criterios de aceptación propuestos por el responsable, confirmados por Luis del Olmo en la revisión de la PR [#71](https://github.com/ACOMPAS-IA/acompas/pull/71).** Los puntos de la sección 0 son elecciones del responsable, confirmadas en esa revisión.

## 0. Puntos confirmados por Luis del Olmo en la revisión de la PR #71

Las fuentes fijan el proveedor de identidad, los roles, el 2FA y la lista blanca, pero no el nombre del realm, los valores concretos de sus políticas ni el reparto exacto con ACO-013 y ACO-015. Esta tabla recoge esas concreciones.

| Nº | Punto | Propuesta | Motivo |
| --- | --- | --- | --- |

## 1. Identificación

- **ID:** ACO-012
- **Nombre:** Realm/configuración

El responsable, el soporte y la revisión, la estimación y las dependencias de este ACO son los de la matriz operativa del Documento Operativo del sprint en curso, que es su fuente única. Esta ficha no los repite.

## 2. Objetivo

Crear y configurar el realm de ACOMPAS sobre Keycloak.

## 3. Incluye

1. Realm de ACOMPAS creado y reproducible: realm `acompas` definido en `infra/keycloak/import/acompas-realm.json`, importado por el `--import-realm` de ACO-011 y reproducible desde un volumen vacío (P1, P11).
2. Configuración base preparada para clientes y usuarios del piloto: roles `paciente` y `administrador`, 2FA obligatorio, política de contraseñas, protección contra fuerza bruta, login con email y cierre del registro, sin clientes de aplicación ni usuarios (P2–P10, P14).
3. Documentación de la configuración relevante: `infra/keycloak/README.md` y la sección de Keycloak de los dos README, con el procedimiento de importación y reimportación (P13).
4. Comprobación local del realm: `scripts/check-realm.sh` (P12).

## 4. Resultado esperado

Con un volumen de Keycloak nuevo, o con uno que todavía no contenga el realm `acompas`, tras `docker compose up -d`:

- `http://localhost:8080/realms/acompas/.well-known/openid-configuration` devuelve un JSON cuyo `issuer` es `http://localhost:8080/realms/acompas` (o el puerto de `KEYCLOAK_PORT`).
- La consola muestra el realm `acompas` habilitado y con nombre visible ACOMPAS.
- El realm tiene los roles `paciente` y `administrador` y ningún rol de aplicación por defecto.
- Un usuario nuevo debe configurar TOTP en su primer acceso y, después, el acceso pide el segundo factor. Lo mismo se aplica si borra la credencial OTP o si se crea por Admin API sin la acción por defecto: el siguiente login obliga a configurarla y no permite entrar solo con contraseña.
- El registro está cerrado; el login con email o usuario está permitido y no admite emails duplicados.
- El realm no contiene usuarios ni clientes de aplicación; solo los clientes integrados de Keycloak.
- `scripts/check-realm.sh` termina con código 0 y `scripts/check-keycloak.sh` sigue comprobando el realm `master`.
- Borrar el volumen y volver a arrancar reconstruye el mismo realm; sin borrarlo, los cambios hechos en la consola se conservan y el JSON no los sobrescribe.
- El backend y PostgreSQL siguen arrancando como antes.

## 5. Fuera de alcance

No forman parte de ACO-012:

- el cliente OIDC y el flujo de login de la aplicación (ACO-013);
- la validación del JWT y los claims en el backend (ACO-014);
- el alta de usuarios, la lista blanca y la resolución email↔UUID (ACO-015; ADR-009);
- el login del frontend (ACO-018);
- usuarios de prueba o reales en el realm importado (P2; ADR-008);
- SMTP, verificación de email y recuperación de contraseña (P6);
- el despliegue de Keycloak fuera del entorno local: modo `start`, TLS, base de datos externa, copias de seguridad e infraestructura (ACO-011; ADR-011);
- el uso de la Admin API de Keycloak (ADR-001);
- cambios en `docker-compose.yml`, en el script de ACO-011 o en la CI (ACO-011; P12);
- cualquier cambio en el backend o en el frontend.

## 6. Relación con otros ACO

Las dependencias de este ACO se consultan en la matriz operativa del Documento Operativo del sprint en curso.

ACO-011 entrega a este ACO el servicio `keycloak` con `--import-realm`, el directorio `infra/keycloak/import/` montado y el `healthcheck`. Este ACO añade allí el JSON del realm.

Este ACO entrega a los siguientes:

- **ACO-013:** el realm `acompas`, su issuer (`http://localhost:8080/realms/acompas`) y los roles `paciente` y `administrador`. ACO-013 añade el cliente OIDC y configura el flujo; los roles de aplicación siguen siendo los de realm.
- **ACO-014:** el issuer y los nombres de los roles que el backend debe reconocer. El UUID del paciente es el identificador nativo de usuario de Keycloak (ADR-001); ACO-014 fija el claim del JWT que lo transporta.
- **ACO-015:** un realm preparado para el alta de usuarios, con roles y 2FA obligatorio. El alta, la lista blanca y la resolución email↔UUID son de ACO-015 (ADR-009). Al crear usuarios no debe desactivar la acción requerida `CONFIGURE_TOTP`, para que el 2FA siga siendo obligatorio.
- **ACO-018 y ACO-032:** el realm y su issuer, a través de la configuración de ACO-013.

## 7. Restricciones técnicas

- Keycloak 26.8.0, la versión fijada en `docker-compose.yml` (ACO-011).
- El realm se importa con `--import-realm` desde `infra/keycloak/import/`, montado en solo lectura (ACO-011).
- El JSON debe ser compatible con el formato de importación de Keycloak 26.
- No se guardan secretos en el JSON: ni usuarios con credenciales, ni secretos de cliente, ni contraseñas. Las credenciales de administrador siguen en `.env` (ACO-011).
- No se usan datos reales (ADR-008).
- Keycloak es el único custodio de la correspondencia email↔UUID; ACOMPAS no almacena el email (ADR-001). Este ACO no crea ninguna tabla ni atributo para esa correspondencia.
- Roles de aplicación: `paciente` y `administrador` (ADR-002, ADR-011). El rol `administrador` no concede acceso a la consola de administración de Keycloak.
- 2FA obligatorio (ADR-011).
- La lista blanca del piloto se guarda en la base de datos de ACOMPAS y la gestiona el administrador; no se implementa en Keycloak (ADR-009; ACO-015).
- Keycloak no usa el PostgreSQL de ACOMPAS (ACO-011 P3; ADR-007).
- No se añaden dependencias ni se modifica la CI.
- Solo entorno local; sin TLS ni configuración de producción (ACO-011; ADR-011).

## 8. Configuración del realm

El realm se define en `infra/keycloak/import/acompas-realm.json`. La tabla fija los valores que este ACO considera contrato; los puntos de la sección 0 son los que no están decididos en una fuente.

| Campo | Valor | Significado |
| --- | --- | --- |
| `realm` | `acompas` | Nombre del realm y segmento del issuer (P1). |
| `enabled` | `true` | Realm activo. |
| `displayName` | `ACOMPAS` | Nombre visible en la consola y el login (P1). |
| `sslRequired` | `external` | HTTPS obligatorio salvo en localhost y redes privadas; el entorno local usa HTTP (P9). |
| `registrationAllowed` | `false` | Sin autorregistro; el alta la hace el administrador (P6; ADR-009). |
| `loginWithEmailAllowed` | `true` | El usuario puede entrar con su email o su nombre de usuario (P6). |
| `duplicateEmailsAllowed` | `false` | Un email no puede estar en dos cuentas (P6). |
| `resetPasswordAllowed` | `false` | Sin recuperación de contraseña por correo mientras no haya SMTP (P6). |
| `verifyEmail` | `false` | Sin verificación por correo mientras no haya SMTP (P6). |
| `editUsernameAllowed` | `false` | El nombre de usuario no se edita desde la cuenta (P6). |
| `bruteForceProtected` | `true` | Activa la protección contra fuerza bruta (P7). |
| `failureFactor` | `5` | Intentos fallidos antes de la espera (P7). |
| `waitIncrementSeconds` | `60` | Incremento de la espera tras cada fallo (P7). |
| `quickLoginCheckMilliSeconds` | `1000` | Ventana para considerar intentos rápidos (P7). |
| `minimumQuickLoginWaitSeconds` | `60` | Espera mínima tras intentos rápidos (P7). |
| `maxFailureWaitSeconds` | `900` | Espera máxima (P7). |
| `maxDeltaTimeSeconds` | `43200` | Ventana en la que se acumulan los fallos (P7). |
| `permanentLockout` | `false` | Sin bloqueo permanente; no hay desbloqueo manual en el Sprint 1 (P7). |
| `passwordPolicy` | `length(12) and notUsername and notEmail` | Longitud mínima y prohibición de usar el usuario o el email como contraseña (P5). |
| `otpPolicyType` | `totp` | Segundo factor por TOTP (P4). |
| `otpPolicyAlgorithm` | `HmacSHA1` | Algoritmo compatible con las aplicaciones autenticadoras habituales (P4). |
| `otpPolicyDigits` | `6` | Código de seis dígitos (P4). |
| `otpPolicyPeriod` | `30` | Código válido 30 segundos (P4). |
| `otpPolicyLookAheadWindow` | `1` | Acepta el código anterior y el siguiente (P4). |
| `browserFlow` | `acompas-browser` | Flujo browser propio con el formulario OTP como `REQUIRED`; impide saltar el 2FA (P4). |
| `requiredActions` | `CONFIGURE_TOTP` con `defaultAction: true`; `delete_credential` con `enabled: false` | Todo usuario nuevo debe configurar TOTP en su primer acceso; las demás acciones integradas se mantienen y se desactiva el borrado de credencial como defensa en profundidad (P4). Si el JSON declara `requiredActions`, debe listar también las acciones integradas de Keycloak 26.8.0 (a verificar contra la documentación oficial). |
| `roles.realm` | `paciente`, `administrador` | Roles de aplicación (P3; ADR-011). |
| `defaultRole` | Sin roles de aplicación | El rol por defecto de Keycloak (`default-roles-acompas`) no incluye `paciente` ni `administrador` (P3). |
| `internationalizationEnabled` | `true` | Activa los idiomas del realm (P10). |
| `supportedLocales` | `["es"]` | Solo español (P10). |
| `defaultLocale` | `es` | Español por defecto (P10). |
| `accessTokenLifespan` | `300` | 5 minutos (P8). |
| `ssoSessionIdleTimeout` | `1800` | 30 minutos de inactividad (P8). |
| `ssoSessionMaxLifespan` | `36000` | 10 horas de sesión máxima (P8). |
| `clients` | Sin clientes de aplicación | Los clientes integrados de Keycloak se mantienen; el cliente de ACOMPAS es de ACO-013 (P2). |
| `users` | Ninguno | El alta y la lista blanca son de ACO-015 (P2; ADR-009). |

El realm conserva los roles y clientes integrados que crea Keycloak. No son roles ni clientes de aplicación y no se modifican en este ACO.

### 8.1 UUID y correspondencia email↔UUID

El UUID del paciente es el identificador nativo de usuario de Keycloak. El realm no define atributos, mappers ni roles para la correspondencia email↔UUID: Keycloak la custodia (ADR-001). El claim del JWT que transporta el UUID se fija en ACO-014 (P14).

## 9. Datos de prueba

Está prohibido utilizar datos reales de pacientes, también como punto de partida (ADR-008).

El realm importado no contiene usuarios, así que no hay emails ni credenciales en Git. Para comprobar el 2FA se puede crear a mano un usuario temporal con un email de dominio reservado, por ejemplo `prueba@example.com`, y borrarlo al terminar. Ese usuario no forma parte del JSON ni del resultado del ACO. Para AC-16 se borra la credencial OTP de ese usuario temporal, se comprueba el siguiente login y se repite con un usuario creado por Admin API sin OTP; ambos se borran al terminar.

## 10. Criterios de aceptación

### AC-01 — Realm importado y reproducible

Tras borrar el volumen `acompas_keycloak_data` (nombre por defecto; el prefijo es el nombre del proyecto Compose) y ejecutar `docker compose up -d`, el servicio `keycloak` queda en `healthy` y `curl -fsS http://localhost:8080/realms/acompas/.well-known/openid-configuration` devuelve un JSON cuyo `issuer` es `http://localhost:8080/realms/acompas` (o el puerto de `KEYCLOAK_PORT`).

### AC-02 — Configuración del realm

`python3 -m json.tool infra/keycloak/import/acompas-realm.json` termina sin errores y la consola muestra el realm `acompas` habilitado, con nombre visible ACOMPAS y los valores de la sección 8.

### AC-03 — Roles

El realm tiene los roles `paciente` y `administrador`. Ninguno de los dos es rol por defecto y los roles integrados de Keycloak siguen existiendo. Se comprueba en la consola.

### AC-04 — 2FA

`CONFIGURE_TOTP` figura como acción requerida por defecto. Un usuario temporal creado a mano (`prueba@example.com`) debe configurar TOTP en su primer acceso; tras configurarlo, un nuevo acceso pide el código. El usuario se borra al terminar.

### AC-05 — Política de contraseñas

Al crear el usuario temporal, Keycloak rechaza una contraseña de menos de 12 caracteres, igual al nombre de usuario o igual al email, y acepta una que cumpla la política (P5).

### AC-06 — Registro, login y recuperación

La página de registro no está disponible; el login acepta email o usuario; no se ofrece recuperación de contraseña; no se permite duplicar un email. Se comprueba en la consola y en la página de login.

### AC-07 — Sin usuarios ni clientes de aplicación

Tras la importación desde un volumen vacío, el realm `acompas` no tiene usuarios y no tiene clientes de aplicación. Solo aparecen los clientes y roles integrados de Keycloak.

### AC-08 — Reproducibilidad e importación

Un cambio hecho en la consola (por ejemplo, el nombre visible) se conserva tras `docker compose restart keycloak` y no lo sobrescribe el JSON. Tras borrar el volumen `acompas_keycloak_data` (nombre por defecto; el prefijo es el nombre del proyecto Compose) y arrancar de nuevo, el realm vuelve a los valores de la sección 8. Se anota el resultado en la PR.

### AC-09 — Sin secretos

El JSON no contiene usuarios, credenciales, contraseñas ni secretos de cliente. El PR no añade `.env` ni credenciales fuera de los valores de desarrollo de ACO-011.

### AC-10 — Documentación

`infra/keycloak/README.md` describe el realm, los roles, el 2FA, la importación y la reimportación. La sección de Keycloak de `README.md` y `README.es.md` indica el nombre del realm, su URL y remite al README de `infra/keycloak/`.

### AC-11 — Comprobación del realm

`scripts/check-realm.sh` termina con código 0 con Keycloak y el realm en marcha, y distinto de 0 con Keycloak parado o sin el realm `acompas`.

### AC-12 — Sin regresiones

`scripts/check-keycloak.sh` sigue pasando (realm `master`), `curl http://localhost:8000/health` devuelve `{"status":"ok"}` y `pytest` del backend pasa.

### AC-13 — Acciones requeridas integradas

La consola muestra, además de `CONFIGURE_TOTP`, las acciones requeridas integradas de Keycloak 26.8.0 (por ejemplo, actualización de contraseña y de perfil), y `CONFIGURE_TOTP` sigue marcada como acción por defecto. Se comprueba en la consola.

### AC-14 — Alcance

El PR solo modifica los componentes de la sección 12.

### AC-15 — Protección contra fuerza bruta

Con un usuario temporal (`prueba@example.com`), cinco intentos fallidos consecutivos de login deshabilitan temporalmente la cuenta: un intento posterior con credenciales correctas sigue rechazándose con el mensaje genérico. Transcurrida la primera ventana de bloqueo (60 s), el mismo usuario puede iniciar sesión sin intervención del administrador, de modo que el bloqueo no es permanente. El usuario se borra al terminar (P7).

### AC-16 — 2FA no eludible

Con un usuario temporal (`prueba@example.com`) que ya tiene TOTP configurado, borrar la credencial OTP desde la consola de cuenta o por Admin API, cerrar sesión y volver a entrar: el login debe obligar a configurar TOTP de nuevo y no debe permitir entrar solo con contraseña. Repetir con un usuario creado por Admin API sin la acción `CONFIGURE_TOTP` y sin OTP: el login también debe obligarlo a configurar TOTP. Si `delete_credential` está desactivada, la API de la consola de cuenta debe devolver `removeable: false` para el OTP y rechazar su borrado; en todo caso, el borrado por Admin API no debe permitir el acceso sin 2FA. Los usuarios se borran al terminar (P4).

## 11. Tests esperados

Como mínimo:

1. `scripts/check-realm.sh` con Keycloak en marcha y parado (AC-01, AC-11).
2. Validación sintáctica del JSON con `python3 -m json.tool` (AC-02).
3. Comprobaciones manuales de AC-03 a AC-08, AC-13, AC-15 y AC-16, con el resultado anotado en la PR. La de AC-15 requiere esperar la primera ventana de bloqueo (60 s). La de AC-16 requiere borrar la credencial OTP de un usuario temporal y comprobar el siguiente login, también con un usuario creado por Admin API sin OTP; la consola de cuenta y la Admin API son suficientes, sin dependencias nuevas.
4. `scripts/check-keycloak.sh`, `curl http://localhost:8000/health` y `pytest` del backend (AC-12).

Las comprobaciones de Keycloak necesitan Docker y descargar la imagen; no forman parte de la CI. `pytest` debe pasar sin red y sin Keycloak.
