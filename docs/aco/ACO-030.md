## 1. Identificación

- **ID:** ACO-030
- **Nombre:** Conversación sobre documento

El responsable, el soporte y la revisión, la estimación y las dependencias de este ACO son los de la matriz operativa del Documento Operativo del sprint en curso, que es su fuente única. Esta ficha no los repite.

## 2. Objetivo

Implementar el flujo conversacional mínimo en el que el usuario consulta sobre un documento clínico sintético previamente procesado.

## 3. Incluye

1. El usuario puede formular una consulta sobre el documento: endpoint `POST /api/conversation` (P3, P4) y página de conversación (P10).
2. El contexto documental llega al LLM de forma controlada: system prompt de ACO-029, documentos entre delimitadores con neutralización (P5, P6), límites de tamaño (P7) y paso obligatorio por el gateway de ACO-027 (ADR-006).
3. Respuesta de Claude visible en la interfaz prevista: la página muestra la respuesta como texto (P10) y cumple el criterio móvil (P12).
4. No se usan documentos reales: tests y comprobaciones con textos sintéticos (sección 9).

## 4. Resultado esperado

Al terminar:

- `POST /api/conversation` recibe documentos anonimizados y una conversación, y devuelve la respuesta de Claude obtenida a través del gateway;
- el `system` es siempre el texto de ACO-029, y los documentos llegan entre sus delimitadores, sin que ningún texto pueda cerrarlos;
- los errores del gateway llegan al cliente como códigos HTTP propios, sin detalles internos;
- nada de la conversación se guarda ni se registra;
- existe una página de conversación que muestra preguntas y respuestas y se usa en un móvil de 360 px sin scroll horizontal;
- el responsable ha comprobado S1 a S9 contra el endpoint con la API real.

## 5. Fuera de alcance

No forman parte de ACO-030:

- validar el JWT y proteger el endpoint (ACO-014; verificación en ACO-032);

## 7. Restricciones técnicas

- Toda llamada a Claude pasa por `LLMGateway` (ADR-006; R-23). Este ACO no importa `anthropic`.
- El LLM solo recibe el texto de los documentos tal como lo envía el cliente, que en el flujo integrado es el anonimizado (P2; ADR-005).
- Ni el endpoint ni el servicio registran el contenido de documentos, preguntas o respuestas (R-04). El registro de metadatos lo hace el gateway.
- Nada se persiste: ni en base de datos, ni en disco, ni en memoria entre peticiones.
- Sin dependencias nuevas, ni en el backend ni en el frontend.
- El gateway se obtiene mediante una dependencia de FastAPI, para poder sustituirlo en los tests por uno con proveedor simulado (T-18).
- La página muestra el texto con el escapado normal de React. No usa `dangerouslySetInnerHTML` ni interpreta Markdown.
- Los estilos de la página van en `ConversationPage.css`, en CSS plano como el de ACO-017, con selectores propios de la página, sin estilos globales y sin anchos fijos mayores de 360 px. No se añade ninguna biblioteca de componentes ni de estilos.
- La página no usa `<main>` como elemento raíz, porque `AppShell` ya lo aporta, ni posicionamiento fijo respecto a la ventana (`position: fixed`), para no solaparse con el pie del disclaimer.

## 8. Contrato de la API de conversación

### 8.1 Petición

`POST /api/conversation`, cuerpo JSON:

```json
{
  "documents": [{ "text": "<texto anonimizado>" }],
  "messages": [{ "role": "user", "content": "¿Qué significa el CA 19-9?" }]
}
```

| Campo | Regla |
| --- | --- |
| `documents` | De 1 a 3 elementos (`MAX_DOCUMENTS`). |
| `documents[].text` | No vacío ni solo espacios; hasta 30.000 caracteres (`MAX_DOCUMENT_CHARS`). |
| `messages` | De 1 a 21 elementos (`MAX_MESSAGES`); alternan `user` y `assistant`; el primero y el último son `user`. |
| `messages[].content` | No vacío ni solo espacios. Un mensaje `user` admite hasta 2.000 caracteres (`MAX_QUESTION_CHARS`), y uno `assistant`, hasta 8.000 (`MAX_ANSWER_CHARS`). |

Se rechazan los campos desconocidos. Una petición que no cumple estas reglas recibe un 422, sin llamar al gateway.

### 8.2 Respuesta

`200`, cuerpo JSON:

```json
{ "answer": "…", "truncated": false }
```

| Campo | Descripción |
| --- | --- |
| `answer` | Texto de la respuesta, sin cambios. |
| `truncated` | `true` si el gateway informa `stop_reason = "max_tokens"`. |

### 8.3 Errores

| Código del gateway | HTTP | `detail` |
| --- | --- | --- |
| `not_configured` | 503 | `llm_not_configured` |
| `rate_limit` | 503 | `llm_busy` |
| `unavailable`, `auth` | 503 | `llm_unavailable` |
| `timeout` | 504 | `llm_timeout` |
| `invalid_request`, `provider_error` | 502 | `llm_error` |
| (respuesta vacía del modelo) | 502 | `llm_error` |

El cuerpo es `{"detail": "<código>"}`. Nunca incluye el mensaje del gateway, el código HTTP del proveedor ni el identificador de petición.

### 8.4 Construcción de los mensajes (P5, P6)

1. Se aplica `neutralize_delimiters` a cada documento y a cada mensaje `user`.
2. El primer mensaje `user` que recibe el gateway es:

   ```text
   <documento_clinico>
   {documento 1}
   </documento_clinico>

   <documento_clinico>
   {documento 2}
   </documento_clinico>

   {primera pregunta}
   ```

3. Los demás mensajes pasan en el mismo orden.
4. `system` es `load_system_prompt().text`.
5. `max_output_tokens` no se envía: se usa el de la configuración del gateway.

`neutralize_delimiters` sustituye por `(documento_clinico)` toda aparición de `<documento_clinico>` o `</documento_clinico>`, sin distinguir mayúsculas y admitiendo espacios entre los signos y el nombre.

### 8.5 Interfaz

`frontend/src/api/conversation.ts` exporta los tipos de la petición y la respuesta y `sendConversation(request): Promise<ConversationResponse>`, que hace `POST` a `/api/conversation` con `fetch`. Si la respuesta no es 2xx, lanza un error con el `detail`.

`ConversationPage` recibe:

| Prop | Tipo | Descripción |
| --- | --- | --- |
| `documents` | `{ text: string }[]` | Documentos anonimizados que se envían en cada pregunta. |
| `send` | `(request) => Promise<ConversationResponse>` | Opcional. Por defecto, `sendConversation`. |

Comportamiento:

- muestra las preguntas y respuestas en orden;
- envía la conversación completa en cada pregunta (P1);
- desactiva el envío mientras espera y si la pregunta está vacía;
- si `truncated` es `true`, añade bajo la respuesta: «La respuesta se ha cortado por su longitud.»;
- ante un error, muestra «No se ha podido obtener respuesta. Inténtalo de nuevo.» y conserva la pregunta para reenviarla;
- no guarda la conversación en el navegador;
- el campo de pregunta y el botón tienen nombre accesible, y la pregunta se envía también con el teclado;
- cumple el criterio móvil de P12.

## 10. Criterios de aceptación

### AC-01 — Estructura

Existen los archivos de la sección 7 y `app/services/conversation/__init__.py` exporta exactamente los nombres de su contrato público.

### AC-02 — Endpoint

`POST /api/conversation` con una petición válida devuelve 200 con `answer` y `truncated`, según la sección 8.2.

### AC-03 — Validación

Las peticiones que incumplen la sección 8.1 (sin documentos, más de 3, textos vacíos o por encima de los límites, conversación que no alterna, que empieza o termina en `assistant`, campos desconocidos) reciben 422 y el gateway no se llama.

### AC-04 — Mensajes al gateway

El gateway recibe como `system` el texto de `load_system_prompt()` y como mensajes los de la sección 8.4, con los documentos entre delimitadores y en orden.

### AC-05 — Neutralización

Un documento o una pregunta que contienen las etiquetas de documento, en cualquiera de sus variantes, llegan al gateway sin ellas. Los únicos delimitadores del primer mensaje son los que añade el backend.

### AC-06 — Errores

Cada código del gateway produce el HTTP y el `detail` de la sección 8.3, sin el mensaje del gateway ni el identificador de petición. Una respuesta vacía produce 502 `llm_error`.

### AC-07 — Truncado

Con `stop_reason = "max_tokens"`, la respuesta lleva `truncated: true`.

### AC-08 — Punto único

El paquete de conversación y el router no importan `anthropic`. El test de punto único de ACO-027 sigue pasando (T-18).

### AC-09 — Sin registro ni persistencia de contenido

Los registros capturados durante una petición correcta y una fallida no contienen el texto de los documentos, de las preguntas ni de la respuesta. El servicio no escribe en base de datos ni en disco, ni guarda estado entre peticiones (R-04).

### AC-10 — Interfaz

Con una función de envío simulada, `ConversationPage` muestra la pregunta y la respuesta, envía la conversación completa en la segunda pregunta, desactiva el envío mientras espera, muestra el aviso de truncado y el mensaje de error, y presenta como texto una respuesta que contiene etiquetas HTML.

### AC-11 — Tests

Los tests de este ACO pasan en Docker local y en CI, sin red y sin clave. El test real se omite en esas condiciones. Los tests del frontend pasan con `npm test`, `npm run lint` y `npm run typecheck`.

### AC-12 — Sin datos reales

Los tests y el código solo contienen textos sintéticos (sección 9).

### AC-13 — Alcance

El PR solo modifica los componentes de la sección 12, no añade dependencias, no cambia el gateway ni el prompt y no implementa autenticación, disclaimer ni persistencia.

### AC-14 — Comprobación con la API real

El responsable ha ejecutado S1 a S9 contra el endpoint (P11) y ha anotado en la PR el resultado de cada sonda, el modelo y la huella del prompt. Este criterio no lo ejecuta el agente.

### AC-15 — Móvil

La página cumple P12. Los tests automáticos cubren la estructura y el estado: nombres accesibles del campo y del botón, envío con teclado, que el elemento raíz no es `<main>` y que las burbujas llevan la clase que parte el texto largo. El scroll horizontal, el corte del texto largo, el área táctil del botón y que el pie no tape el campo ni el botón se comprueban a mano, porque jsdom no calcula el layout: el responsable monta la página temporalmente en `App.tsx`, dentro de `AppShell` si ACO-017 ya está en `main`, sin subir ese cambio, la revisa a 360 px y en escritorio y lo anota en la PR.
