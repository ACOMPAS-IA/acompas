## 1. Identificación

- **ID:** ACO-019
- **Nombre:** API client

El responsable, el soporte y la revisión, la estimación y las dependencias de este ACO son los de la matriz operativa del Documento Operativo del sprint en curso, que es su fuente única. Esta ficha no los repite.

## 2. Objetivo

Crear el cliente del frontend para consumir el API backend autenticado.

## 3. Incluye

1. Un cliente centralizado para las llamadas al backend que adjunta el JWT de ACO-018 en cada petición (P1, P4).
2. El mecanismo de vuelta al login cuando la sesión no es válida, sin bucles ni transiciones duplicadas (P3).
3. El envoltorio autenticado de la conversación de ACO-030 (P2).
4. El contrato de integración documentado para ACO-032, incluido el uso del cliente con la API de anonimización de ACO-024 (P2).
5. La configuración local del proxy de desarrollo y su comprobación (P1).

## 4. Resultado esperado

Al terminar:

- existe `frontend/src/api/client.ts` con `apiRequest`, que obtiene el token antes de cada petición y añade `Authorization: Bearer <token>`;
- `sendConversation` usa ese cliente y sigue respetando el contrato de ACO-030;
- sin token o con un 401, la aplicación vuelve a la pantalla de login una sola vez, limpia la sesión local y no deja un `getUser()` tardío que restaure la sesión;
- un 403, 422, 503 o 504 no cierran la sesión y llegan como `ApiError` con un código permitido o `request_failed`;
- el frontend llama a `/api/...` en el mismo origen y el proxy de Vite lo reenvía al backend, tanto con `npm run dev` como en Compose;
- `frontend/src/api/README.md` documenta el cliente, los errores, el proxy y cómo ACO-032 debe llamar a `/api/anonymization`;
- `npm run lint`, `npm run typecheck` y `npm test` pasan, y la CI sigue en verde;
- no se añaden dependencias, no se toca el backend y no se usan datos reales ni secretos.

## 8. Contrato del cliente

### 8.1 Transporte y proxy

- El cliente usa rutas relativas: `POST /api/conversation`, `POST /api/anonymization`.
- `vite.config.ts` configura `server.proxy['/api']` con destino `API_PROXY_TARGET`.
- Valor por defecto: `http://localhost:8000`, para ejecutar Vite en el host.
- En Compose, el servicio `frontend` recibe `API_PROXY_TARGET: http://backend:8000`, porque dentro de la red de Compose el backend se resuelve por su nombre.
- La variable se lee en la configuración de Vite con `loadEnv`, no con `process` directo, para no añadir `@types/node`.
- No se modifica el backend ni se añade middleware CORS. El navegador no hace peticiones cross-origin.

### 8.2 Cliente centralizado

```ts
type ApiRequestOptions = {
  allowedDetails?: readonly string[]
}

function apiRequest<T>(
  path: string,
  init?: RequestInit,
  options?: ApiRequestOptions,
): Promise<T>
```

Comportamiento:

1. Llama a `getAccessToken()`.
2. Si devuelve `null` o falla, emite `acompas:session-expired`, no llama a `fetch` y lanza `SessionExpiredError`.
3. Añade `Authorization: Bearer <token>`, `Accept: application/json`, `credentials: 'omit'` y `cache: 'no-store'`.
4. No permite que el llamador sobrescriba `Authorization`; si lo intenta, prevalece el token.
5. Si `fetch` falla por red, lanza `ApiError` con `status: 0` y `detail: request_failed`.
6. Si la respuesta es 401, emite el evento y lanza `SessionExpiredError`.
7. Si es 403, lanza `ApiError(403, 'forbidden')`.
8. Si no es 2xx, lee `detail` y lo conserva solo si está permitido; si no, usa `request_failed`.
9. Si es 2xx, devuelve el JSON. Un JSON inválido se convierte en `ApiError` con `detail: request_failed`.

### 8.3 Errores

| Situación | Clase | `status` | `detail` | Efecto |
| --- | --- | --- | --- | --- |
| Sin token o `getAccessToken` falla | `SessionExpiredError` | 401 | `unauthorized` | Vuelve al login |
| 401 del backend | `SessionExpiredError` | 401 | `unauthorized` | Vuelve al login |
| 403 del backend | `ApiError` | 403 | `forbidden` | No cierra sesión |
| Código documentado de la petición | `ApiError` | HTTP real | Código permitido | No cierra sesión |
| Código no documentado o cuerpo no válido | `ApiError` | HTTP real | `request_failed` | No cierra sesión |
| Error de red | `ApiError` | 0 | `request_failed` | No cierra sesión |
| JSON inválido en una respuesta 2xx | `ApiError` | HTTP real | `request_failed` | No cierra sesión |

Códigos comunes permitidos: `unauthorized`, `forbidden`, `auth_unavailable`.

Códigos de conversación (ACO-030): `llm_not_configured`, `llm_busy`, `llm_unavailable`, `llm_timeout`, `llm_error`.

Códigos de anonimización para ACO-032 (ACO-024): `invalid_request`, `text_too_long`, `anonymization_not_configured`.

### 8.4 Sesión caducada

- Evento: `acompas:session-expired`.
- `notifySessionExpired()` solo emite el evento; no guarda estado.
- `useAuthSession` mantiene un `ref` de expiración ya gestionada y un contador de generación.
- Al recibir el evento: si ya se gestionó, no hace nada; si no, marca la expiración, incrementa la generación, pasa a `anonymous`, fija el aviso y llama a `clearSession()`.
- `bootstrap()` captura la generación antes de sus `await` y descarta su resultado si cambió, de modo que un `getUser()` tardío no puede volver a `authenticated`.
- La expiración se reinicia solo después de un `signIn()` o un callback completados con éxito; no se reinicia porque `getUser()` devuelva un usuario.
- `clearSession()` ejecuta `removeUser()` y no redirige a Keycloak.
- El aviso visible es «La sesión ha caducado. Vuelve a iniciar sesión.» y no incluye token, claims ni detalles del proveedor.

### 8.5 Conversación

`frontend/src/api/conversation.ts` mantiene los tipos y `SendConversation` de ACO-030 y usa `apiRequest`:

```ts
sendConversation(request) // POST /api/conversation con Authorization
```

- `ConversationError` se conserva para los errores del endpoint y lleva el `detail` permitido.
- `SessionExpiredError` se propaga sin convertir, para que la transición de sesión no se oculte.
- `ConversationPage` no cambia: su función de envío por defecto pasa a estar autenticada.

### 8.6 Contrato para ACO-032

`frontend/src/api/README.md` documenta:

## 10. Criterios de aceptación

### AC-01 — Cliente centralizado

Existe `apiRequest` en `frontend/src/api/client.ts`; `sendConversation` lo usa y no llama a `fetch` directamente. Los tipos y el contrato de ACO-030 se conservan.

### AC-02 — Autenticación

Toda petición llama a `getAccessToken()` antes de `fetch`, añade `Authorization: Bearer <token>` y no permite que el llamador lo sobrescriba. Sin token no se llama a `fetch`.

### AC-03 — Sesión caducada

Sin token o con 401 se vuelve a la pantalla de login una sola vez, se limpia la sesión local y no se restaura `authenticated` por un `getUser()` tardío. Dos 401 concurrentes no duplican la transición ni la limpieza. Un 403, 422, 503 o 504 no cierran sesión.

### AC-04 — Errores sin fugas

Solo se conservan los códigos documentados para la petición. Cualquier otro `detail`, cuerpo no JSON o error de red se convierte en `request_failed`. Un 401 se normaliza a `unauthorized` y un 403 a `forbidden`. El token, los claims y el cuerpo original no aparecen en errores ni logs.

### AC-05 — Proxy

Las llamadas usan `/api/...` y funcionan a través de `http://localhost:5173` con el backend en marcha. En Compose, `API_PROXY_TARGET` apunta a `http://backend:8000`. No se modifica el backend ni se añade CORS. La comprobación manual con `curl` verifica el proxy y el 401; la ausencia de problema CORS se comprobará en el navegador cuando el flujo autenticado esté disponible.

### AC-06 — Contrato para ACO-032

`frontend/src/api/README.md` y la sección 8 de esta ficha documentan el cliente, la autenticación, los errores, la sesión caducada, el proxy y el ejemplo de anonimización. ACO-032 puede añadir su envoltorio sin modificar `client.ts`.

### AC-07 — Sin regresiones

`npm run lint`, `npm run typecheck` y `npm test` pasan. Los tests existentes del frontend, incluidos los de `ConversationPage`, `AuthGate` y `App`, siguen pasando. El job `frontend` de la CI sigue en verde.

### AC-08 — Alcance y seguridad

El PR solo modifica los componentes de la sección 12. No se añaden dependencias, no se tocan el backend, Keycloak, `scripts/` ni la CI. No hay datos reales, secretos, tokens en logs ni persistencia distinta de `sessionStorage`.
