## 1. Identificación

- **ID:** ACO-024
- **Nombre:** API anonimización

El responsable, el soporte y la revisión, la estimación y las dependencias de este ACO son los de la matriz operativa del Documento Operativo del sprint en curso, que es su fuente única. Esta ficha no los repite.

## 2. Objetivo

Exponer el servicio de anonimización mediante una interfaz HTTP interna del backend.

## 3. Incluye

1. Un endpoint HTTP que recibe texto y devuelve el resultado de la anonimización conforme al contrato de ACO-020 y a los estados de ACO-023.
2. La validación del cuerpo de la petición y del tamaño del texto.
3. La conversión de los errores del servicio y de la configuración en respuestas HTTP con códigos propios.
4. La protección del endpoint con el JWT validado de ACO-014.
5. La garantía de que ninguna respuesta, incluidos los errores de validación, contiene el texto original.
6. Las pruebas del contrato HTTP, sin modelo y sin red, y la documentación del endpoint en esta ficha.

## 4. Resultado esperado

Al terminar:

- existe `POST /api/anonymization`, documentado en esta ficha y en OpenAPI;
- recibe `{"text": "<texto>"}` y devuelve `status`, `confidence`, `anonymized_text`, `entities_count` y `reason`;
- `validado` devuelve el texto anonimizado; `retenido` e `ilegible` no devuelven texto y explican el motivo;
- un cuerpo inválido o un texto demasiado largo devuelve 422 con un código, sin repetir el texto recibido;
- una configuración de umbrales inválida devuelve 503 con un código;
- sin JWT válido no se puede invocar el endpoint;
- no se persiste nada, no se registra contenido y no se añaden dependencias;
- los tests de la sección 11 y los existentes de `backend/tests/` pasan en Docker local y en CI.

## 5. Fuera de alcance

No forman parte de ACO-024:

- la obtención del texto desde un PDF, JPG o PNG y el OCR (PD-07 sigue abierto; el OCR es de Sprint 2, ADR-004);
- la persistencia del original o del resultado retenido, el registro de auditoría y el derecho al olvido (ACO-025 y Sprint 2);
- la modificación del servicio, la política, la confianza, la sustitución o el contrato de ACO-023;
- el cliente de API del frontend (ACO-019 y ACO-032);
- el contrato de conversación (ACO-030, ya fijado);
- la interfaz de usuario y la pantalla de validación (ACO-032);
- los Niveles 2 y 3 de anonimización;
- dependencias nuevas.

## 6. Relación con otros ACO

Las dependencias de este ACO se consultan en la matriz operativa del Documento Operativo del sprint en curso.

- **ACO-020** define el contrato de entrada y salida del servicio sobre texto; ACO-024 lo expone por HTTP.
- **ACO-023** entrega `AnonymizationService.anonymize()` con los estados, la confianza, el texto anonimizado, el recuento y el motivo. ACO-024 no cambia ese contrato.
- **ACO-030** consume el texto anonimizado: el cliente envía a conversación el `anonymized_text` que devuelve este endpoint. ACO-024 no cambia el contrato de conversación.
- **ACO-032** integra la subida, la llamada a este endpoint y la conversación; comprueba que el endpoint está protegido.
- **ACO-025** verifica que no se persiste el original ni el resultado retenido; ACO-024 no introduce persistencia.
- **ACO-026** amplía la cobertura de pruebas de la anonimización, incluida la respuesta de la API.

## 7. Restricciones técnicas

- FastAPI y Pydantic son dependencias ya presentes; no se añade ninguna.
- La autenticación se resuelve con la dependencia `get_current_user` de ACO-014.
- La configuración de los umbrales se lee en cada llamada dentro del servicio; el endpoint no la duplica ni la fija.
- El endpoint no persiste ni registra el texto, el nombre de un fichero ni fragmentos del documento.
- Ninguna respuesta devuelve el texto original, tampoco los errores de validación.
- El modelo y el motor NLP no se tocan: se reutiliza el `AnonymizationService` de ACO-023.
- Los datos de prueba son sintéticos (ADR-008).

## 8. Contrato de la API de anonimización

### 8.1 Ruta y método

```
POST /api/anonymization
```

El endpoint es interno del backend, pero lo consume el cliente de la interfaz mínima con el JWT del usuario. No se publica fuera de la aplicación.

### 8.2 Entrada

```json
{
  "text": "<texto extraído del documento>"
}
```

- `text` es obligatorio y debe ser una cadena.
- Se admite la cadena vacía y una cadena formada solo por espacios: el servicio las trata como documento ilegible (ADR-013).
- El máximo es de 30.000 caracteres (P2).
- La petición se valida antes de invocar al servicio.

### 8.3 Salida

Se reutiliza `AnonymizationResult` de ACO-023:

| Campo | Tipo | Contenido |
| --- | --- | --- |
| `status` | `validado`, `retenido` o `ilegible` | Desenlace del procesamiento. |
| `confidence` | número entre 0 y 1, o `null` | Confianza del documento; `null` si es ilegible. |
| `anonymized_text` | cadena o `null` | Texto con etiquetas solo si `validado`; `null` en los otros dos estados. |
| `entities_count` | objeto tipo → entero | Hallazgos finalmente anonimizados por tipo; vacío si no hay texto anonimizado. |
| `reason` | cadena o `null` | `null` si `validado`, `baja_confianza` si `retenido`, `texto_vacio` si `ilegible`. |

Ejemplos con valores sintéticos de ACO-051:

```json
{
  "status": "validado",
  "confidence": 0.93,
  "anonymized_text": "Paciente: [PACIENTE]. DNI: [DNI].",
  "entities_count": {"PERSON": 1, "ES_DNI": 1},
  "reason": null
}
```

```json
{
  "status": "retenido",
  "confidence": 0.42,
  "anonymized_text": null,
  "entities_count": {},
  "reason": "baja_confianza"
}
```

```json
{
  "status": "ilegible",
  "confidence": null,
  "anonymized_text": null,
  "entities_count": {},
  "reason": "texto_vacio"
}
```

Los tres desenlaces devuelven 200 (P3).

### 8.4 Errores

| Caso | HTTP | `detail` |
| --- | --- | --- |
| Sin token o token inválido | 401 | `unauthorized` (ACO-014) |
| Token sin rol de aplicación | 403 | `forbidden` (ACO-014) |
| Autenticación no configurada | 503 | `auth_unavailable` (ACO-014) |
| JSON mal formado, falta `text` o `text` no es una cadena | 422 | `invalid_request` |
| `text` supera los 30.000 caracteres | 422 | `text_too_long` |
| Umbrales de anonimización inválidos | 503 | `anonymization_not_configured` |
| Fallo inesperado | 500 | Sin detalle (respuesta por defecto del framework) |

Los 422 devuelven un único código, no la lista de errores de validación ni el valor recibido (P5). El cuerpo de un 500 no incluye el texto ni detalles internos.

### 8.5 Autenticación

El endpoint se registra con `Depends(get_current_user)`, como el resto de endpoints de negocio. Sin un JWT válido con alguno de los roles de aplicación no se ejecuta el servicio (ADR-011). Los códigos y el cuerpo de los errores de autenticación son los de ACO-014.

### 8.6 Implementación

- El router vive en `backend/app/api/anonymization.py` y se registra en `backend/app/main.py`.
- El servicio se obtiene con una dependencia `get_anonymization_service()`, cacheada para que el `AnalyzerEngine` se cargue una sola vez. En los tests se sustituye con `app.dependency_overrides`, de modo que las pruebas del contrato no cargan el modelo.
- `AnonymizationConfigurationError` se traduce a 503 `anonymization_not_configured`, sin encadenar el mensaje original.
- El handler de `RequestValidationError` comprueba la ruta: para `/api/anonymization` devuelve `invalid_request` o `text_too_long`; para el resto delega en el handler por defecto.
- No se añade un handler genérico de 500: se mantiene la respuesta por defecto, que no incluye detalle.
- El endpoint no escribe en la base de datos, no guarda el original y no registra contenido.

### 8.7 Privacidad de la respuesta

- `entities_count` solo contiene tipos de entidad y recuentos; no incluye valores, posiciones ni fragmentos.
- `anonymized_text` es el texto con etiquetas, nunca el original.
- Los errores de validación no repiten el valor recibido.
- El endpoint no registra el cuerpo de la petición.

## 9. Datos de prueba

Está prohibido utilizar datos reales de pacientes, también como punto de partida (ADR-008).

Los tests usan frases cortas con los valores sintéticos de ACO-051:

- DNI `12345678Z`;
- nombre `Rosario Albendea Quintanar`;
- etiquetas de anonimización como `[PACIENTE]`, `[SANITARIO_1]` o `[DNI]`.

No se modifican los documentos ni el manifiesto de ACO-051. Las pruebas del 500 usan un texto sintético marcado para comprobar que no se filtra.

## 10. Criterios de aceptación

### AC-01 — Ruta y documentación

Existe `POST /api/anonymization`, registrado en `backend/app/main.py`, documentado en esta ficha y visible en el esquema OpenAPI de la aplicación.

### AC-02 — Entrada y límite

El endpoint recibe `{"text": "<cadena>"}`. La cadena vacía se admite y produce `ilegible`. El máximo es de 30.000 caracteres: 30.000 se aceptan y 30.001 devuelven 422 `text_too_long`. El límite es una decisión nueva, pendiente de confirmar (P2).

### AC-03 — Contrato de salida

Los tres estados devuelven 200 con `status`, `confidence`, `anonymized_text`, `entities_count` y `reason`. Solo `validado` lleva `anonymized_text`; `retenido` e `ilegible` lo devuelven como `null` y con su motivo.

### AC-04 — Sin texto original

Ninguna respuesta contiene el texto recibido ni fragmentos de él: ni la de `validado` (que lleva el anonimizado), ni las de `retenido` e `ilegible`, ni los 422, ni el 500.

### AC-05 — Validaciones y errores

Un cuerpo mal formado, la falta de `text` o un tipo incorrecto devuelven 422 `invalid_request`; un texto demasiado largo, 422 `text_too_long`; una configuración de umbrales inválida, 503 `anonymization_not_configured`; un fallo inesperado, 500 sin detalle. Los 422 no incluyen el valor recibido.

### AC-06 — Autenticación

Sin token válido el endpoint devuelve 401; con un token sin rol de aplicación, 403; sin configuración de autenticación, 503. Los códigos y el cuerpo son los de ACO-014.

### AC-07 — Sin persistencia ni registro de contenido

El endpoint no escribe en la base de datos, no guarda el original ni el resultado retenido y no registra el texto ni fragmentos.

### AC-08 — Servicio inyectable y sin modelo en los tests

El endpoint obtiene el servicio mediante una dependencia sustituible. Los tests del contrato usan un analyzer falso y no cargan el modelo. El analyzer real se instancia una sola vez por proceso.

### AC-09 — Alcance

El PR solo modifica los componentes de la sección 12.

### AC-10 — Tests y CI

Los tests de la sección 11 pasan sin red y sin modelo, y el resto de `backend/tests/` sigue pasando. La CI está en verde.

## 11. Tests esperados

Como mínimo, en `backend/tests/anonymization/test_api.py`:

1. `validado`: 200, etiquetas en `anonymized_text`, `entities_count` correcto y sin valores originales en la respuesta.
2. `retenido`: 200, `anonymized_text` ausente, `reason` `baja_confianza` y `confidence` presente.
3. `ilegible`: cadena vacía, solo espacios y solo saltos de línea devuelven 200 con `reason` `texto_vacio`, sin llamar al analyzer.
4. Cuerpo inválido: JSON mal formado, falta `text` y `text` no es cadena devuelven 422 `invalid_request` sin repetir el texto.
5. Texto de 30.001 caracteres devuelve 422 `text_too_long` sin repetir el texto.
6. Frontera aceptada: 30.000 caracteres con un analyzer sin detecciones devuelven 200 `validado`, confianza 1,0 y el texto intacto.
7. Umbrales inválidos por entorno devuelven 503 `anonymization_not_configured` sin invocar al analyzer.
8. Sin token devuelve 401; la ruta aparece en `/openapi.json`.
9. Fallo interno: un servicio sustituido que lanza una excepción, con `TestClient(app, raise_server_exceptions=False)`, devuelve 500 y la respuesta no contiene el texto de entrada.
10. La respuesta de los casos funcionales no contiene los valores sintéticos del manifiesto (DNI y nombre).

Los tests 1 a 10 deben pasar sin red, sin modelo y sin servicios externos.
